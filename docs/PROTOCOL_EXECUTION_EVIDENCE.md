# Protocol execution evidence (BUILD 03.1)

Audit date: 2026-09-26. This document concerns read-only research and dry-run planning only. BUILD 03.1 adds no wallet, signing, order submission, or funds path.

## Evidence model

Execution rules are not just values. Each `ProtocolRuleEvidence<T>` records a value, authority, source, observation time, network, applicability, and confidence. The authority classes distinguish official documentation, live protocol metadata, maintained SDK behavior, empirical live observations, secondary documentation, operator overrides, and fixtures. Conflicts are retained instead of erased. A higher-authority source can resolve a lower-authority disagreement, but the disagreement remains visible; disagreement at the highest available authority is `CONFLICT`.

`STRICT_MAINNET` accepts only `OFFICIAL_DOCUMENTATION` that explicitly applies to HIP-4/outcomes, or `LIVE_PROTOCOL_METADATA` observed on mainnet, for every rule required to make an order valid. Generic official examples with unclear scope are preserved as evidence but do not pass applicability checks. `DEVELOPMENT_DRY_RUN` can accept labelled maintained-SDK evidence, explicit fixture metadata, or explicitly configured operator overrides. Empirical observations do not establish execution-critical rules under either policy. The web preview is always strict; only deterministic fixtures use the development policy.

## What Hyperliquid publishes

Hyperliquid's [tick and lot-size documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/tick-and-lot-size) describes size validity as a function of an asset's `szDecimals`. It says that the value is obtained from asset metadata and gives the spot price rule of five significant figures and a maximum of `8 - szDecimals` decimal places. The [asset ID documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/asset-ids) says outcome assets share most spot trading implementation details and identifies the outcome coin/token/asset ID encodings.

The [Info API documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint) documents public L2 books. The probe's read-only `recentTrades` Info query returned data on mainnet, but that request type was not found in the current public Info docs during this audit, so it is reported as observed API behavior, not as a documented endpoint contract. Book and trade quantity strings describe displayed or executed quantities, not the complete set of accepted order quantities. They do not return a side's `szDecimals` field. The official [Spot API reference](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/spot) shows `szDecimals` on spot-token metadata. It does not document an outcome-side precision mapping. That page currently labels `outcomeMeta` as testnet-only; during this audit the mainnet Info endpoint nevertheless returned an `outcomeMeta` payload. This documentation/behavior mismatch is recorded rather than generalized to testnet.

## Mainnet metadata observations

The evidence probe reads `outcomeMeta`, `spotMeta`, `spotMetaAndAssetCtxs`, and `allMids`; then it inspects up to 20 future-dated outcomes, selected round-robin across the underlying labels present in their descriptions, and queries both side books and recent trades. It reports actual counts, failures, fractional quantity observations, quote-token labels, timestamp, and a stable content-derived evidence snapshot identity. It is a bounded sample, not a proof about every HIP-4 outcome.

On the audit date, the mainnet `outcomeMeta` schema contained outcome names/descriptions, side specs, quote token and other market fields, but no `szDecimals` at the outcome or side-spec level. `spotMeta` and `spotMetaAndAssetCtxs` did not provide `+<outcome encoding>` tokens that could join an outcome side to a spot token's precision. All-mids and the observed book/trade responses provided prices and quantities but no precision field. Mainnet metadata showed `USDC` as the quote token during the sampled read; this is a dated observation, not a claim about every venue or future outcome.

Book and trade quantities were checked as exact decimal strings after removing insignificant trailing zeroes. Even when every observed quantity is integral, that only means integer quantities were observed in that sample. It does not show that fractional quantities would be rejected, nor whether `szDecimals` is zero. Address-scoped user balance and position endpoints were not queried because no representative account address was supplied. A user's balances or positions would not establish the protocol lot rule in any case.

At the 2026-09-26 19:46 UTC probe run, `outcomeMeta` returned 233 outcomes and no outcome-level or side-spec `szDecimals`; `spotMeta` contained 503 tokens and neither spot metadata response contained `+`-named outcome tokens. `allMids` contained 466 `#`-prefixed outcome coins, and all current outcomes reported `USDC` as `quoteToken`. The bounded active sample covered 20 outcomes / 40 sides, 770 L2 levels, and 214 recent trades; there were no read failures and no fractional quantities in either observed set. Snapshot identity: `contour-evidence-v1:fnv1a64:e1b5c34ac0db5f56`. These are mainnet observations at one timestamp, not proof about order acceptance, an exhaustive sample, or testnet.

## Maintained SDK audit

The current maintained [`@outcome.xyz/hip4` source](https://github.com/Outcome-xyz/hip4/blob/main/src/adapter/hyperliquid/trading.ts) imports `stripZeros`, `formatPrice`, and `MIN_NOTIONAL`. It strips trailing zeroes from the quantity string, formats a limit price to its price-tick convention, and checks minimum notional (and optional minimum shares when a mark is passed). It does not derive HIP-4 `szDecimals` from outcome metadata, nor does it validate quantity decimal places against an outcome-side precision. Quantity serialization and exchange acceptance are downstream of its client-side preparation. Its [pricing source](https://github.com/Outcome-xyz/hip4/blob/main/src/adapter/hyperliquid/pricing.ts) defines `MIN_NOTIONAL = 1` and comments that a Hyperliquid network upgrade reduced it from 10 to 1. Its `tests/unit/pricing.test.ts` exercises the minimum constant, `getMinShares`, tick handling, and trailing-zero formatting; `tests/unit/trading-validation.test.ts` covers price formatting and quantity trailing-zero stripping, not an outcome `szDecimals` validation contract.

The repository changelog's [`1.2.0-beta` entry](https://github.com/Outcome-xyz/hip4/blob/main/CHANGELOG.md) is dated 2026-09-05 and says to consume the release only after the network upgrade is live. The current README's `minOrderNotional: 10` example describes a configurable client-side floor that must be at least the SDK's protocol constant; it does not itself establish a $10 protocol rule. The changelog is maintained-SDK evidence for the $1 value, not an independent Hyperliquid announcement.

The current official [Hyperliquid Python SDK](https://github.com/hyperliquid-dex/hyperliquid-python-sdk) treats perp precision as coming from `meta` and spot precision as coming from `spot_meta`; its general order wire conversion serializes price and size but does not infer HIP-4 size precision. Its `float_to_wire` function formats to eight decimals and rejects values that would be rounded; that generic serialization behavior is not outcome-specific lot validation. It provides no second source for HIP-4 `szDecimals` or the HIP-4 minimum notional.

## Minimum-notional evidence

The official generic [Exchange endpoint order example](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint) currently includes an error response saying an order must have minimum value `$10`. The example is not labelled HIP-4/outcomes-specific. Therefore it is authoritative evidence that the generic example says `$10`, but not enough to establish that a HIP-4 outcome-side order has that rule.

The maintained Outcome.xyz SDK source and changelog claim a HIP-4-specific `$1` minimum after an upgrade. Older ecosystem documentation also asserts `$10` (for example, the [perps-studio HIP-4 v2 guide](https://github.com/perps-studio/hip-4/blob/main/docs/version-upgrades/v2.md)); that is secondary and may be stale. Contour records the general official `$10` example, the HIP-4-specific SDK `$1` claim, and the older secondary `$10` claim as separate provenance. The official generic example may be stale or may apply to outcomes; the reviewed official docs do not resolve its applicability. Until an official HIP-4-specific source or authoritative live protocol signal settles the scope, strict mainnet blocks minimum-notional readiness and does not promote either value to the HIP-4 rule.

## Read-only preflight and network scope

The official Info API supports public metadata and market data reads, not a documented unsigned “would this order pass precision/notional checks?” preflight. The documented Exchange `order` action is a POST containing action, nonce, and required signature; its example response is an actual order result/error, not a read-only validation mode. The exchange endpoint is not called. No order, signed or unsigned, is submitted. Current testnet parity for the outcome-specific schema and rules was not established; mainnet evidence is not transferred to testnet or vice versa.

## Operator overrides

Development processes may explicitly set `CONTOUR_EXECUTION_TRUST_POLICY=DEVELOPMENT_DRY_RUN` plus `CONTOUR_OUTCOME_SZ_DECIMALS=0..8` and/or `CONTOUR_MIN_NOTIONAL=<positive decimal>`. Unset variables mean no override. A value without the explicit development policy is rejected. Reports identify every override as `OPERATOR_OVERRIDE`, say it is not protocol-discovered, and preserve its variable as source. The web application does not read these values and cannot activate them from the browser.

## Why Contour refuses to guess

An observed book or SDK implementation is not the exchange's execution rule. Hard-coding integer contracts could produce a plan that differs from the accepted order quantity grid; treating an SDK's upgrade note as official could misclassify a changing minimum. Therefore the live preview shows the payoff proof separately from execution readiness and blocks until every required protocol rule has sufficient authority.

Before mainnet signing can even be considered, Contour needs: a current official outcome-side lot-precision source or a live authoritative metadata mapping; official minimum-notional evidence or an explicitly justified conservative treatment; independently tested mainnet/testnet applicability; versioned parser and trust-policy tests; and a separate security review of any future signing/broadcast design. BUILD 03.1 does not begin BUILD 04 and does not enable any signing or submission.
